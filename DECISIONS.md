A button either shows the system prompt (first time) or opens the right System Settings pane (`x-apple.systempreferences:…?Privacy_Microphone|Privacy_Accessibility|Privacy_ScreenCapture`, fixed URLs only). The window polls once a second while the step is open and on focus, so a toggle in System Settings flips the status live; Screen Recording usually needs a relaunch, so it offers "Reopen Hikari" (`relaunch_app`). Accessibility and Screen Recording are labelled optional, "for Mac control" (M7). Status changes are logged (`permissions: microphone=… accessibility=… screen_recording=…`).
  - **Verified in the release app:** first launch showed the welcome window; the log read `microphone=Granted accessibility=NotDetermined screen_recording=Granted` on this Mac. Not verified: the live flip after a real grant (I won't change security settings), the AX prompt, and how macOS treats these grants across rebuilds (see signing below).

  The stage code belongs to the M3 owner, so these are **recommendations, not changes**:
  1. **Live2D: try `antialias: false`** (`src/avatar/live2d/Live2DAvatar.ts`, HEAD line 83, `antialias: true`). MSAA on an 840×1280 drawing buffer is resolved every frame; Live2D art has textured edges, and Iki (no MSAA) idles 10 points cheaper. Expect 2–5 points idle; check edges in the Studio.
  2. **Idle resolution 1.5×** instead of 2× for Live2D (`Live2DAvatar.ts` HEAD line 82, `resolution: Math.min(2, devicePixelRatio)`), switched with the tier: 44 % fewer pixels to draw and composite. Expect a few points of WebKit compositing; needs an eye test (the user rejected visibly worse idle before).
  3. **Pause on occlusion/screen lock** (`src-tauri/src/stage.rs`): emit `stage://visible false` on `NSWindowDidChangeOcclusionStateNotification` / `com.apple.screenIsLocked`. Saves the whole render cost (17–28 %) while the screen is locked or the display sleeps, if WebKit isn't already throttling rAF there (measure first).
  4. **One readback per hit test** (HEAD `Live2DAvatar.ts:318`, `IkiAvatar.ts:301`): read a 7×7 block once instead of up to five 1-px `readPixels` (five GPU syncs) on every cursor event over the window. Only matters while hovering.
  5. **Per-frame allocations in `StageRuntime.loop`** (`src/stage/runtime.ts`): `scheduled.find` with a new closure, `visemesToLive2D(vis)` built twice, `LipSyncEngine.sample` spreading a new object every frame even when silent. Under 1 point; worth it only together with the above.
  6. `src/stage/frameScheduler.ts` itself is cheap (no allocations). The remaining floor is WebKit (~9 % with zero frames, see 2026-11-20); the < 3 % target still needs a different renderer.

## 2026-11-26 — M5/M6 (A): Memories window and Voice Lab

- **No schema change.** Both windows work within protocol 0.2.0; what B needs is listed below. B please review.
- **Memories** (`src/memory/`). Search is debounced (250 ms) into `memory.query {q, kind, namespace, limit: 40, offset}`; paging by offset as the list end scrolls into view. Namespace is the active character (same localStorage key as Chat) or "All characters" (no namespace). Edits send the whole item as `memory.upsert` (new `text`, `updatedAt` in the item's own time unit); deletes (single or multi-select, behind a confirmation sheet) send `memory.delete {ids}`. Both show at once and are rolled back on failure.
  - **Correlation without ids.** The panel bridge doesn't forward envelope ids, so `memory.results` are matched to queries **in the order they were sent**. A reply to a query sent after an edit settles that edit. A reply for an older filter is dropped. **B: answer `memory.query` in order, one `memory.results` per query.**
  - **Failures.** **B: on a failed request send `error {code: "memory.query_failed" | "memory.upsert_failed" | "memory.delete_failed", message}`** (underscore instead of the dot is accepted). The UI rolls back the oldest pending op of that kind. Errors don't name the item, so setting `replyTo` and forwarding it through the bridge would make this exact (later protocol change).
  - **Timestamps** may be seconds or ms (below 1e12 is read as seconds). `total` in `memory.results` is optional but wanted (the header shows it; paging falls back to "the page was full").
  - Offline (core not connected) shows an explanation and nothing else. Sample data exists only in the DEV browser preview (`devCore.ts`, a stand-in core; `#/memory?core=manual` to drive it by hand, `?core=offline` for the offline state; `hikariMemory.failNext = true` to see a rollback).
- **Voice Lab** (`src/voicelab/`). Ops on `voice_lab.event {op, voiceId, data}`, proposed by A (full table in `ops.ts`):
  - UI → core: `voices.list`, `voice.create {name, language}` (UI picks the voiceId), `voice.delete`, `consent.check`, `consent.record`, `script.get {language}`, `clip.saved`, `train.start`, `train.cancel`, `eval.get {rerun?}`, `ab.next`, `ab.result`.
  - Core → UI: `voices.list {voices}`, `voice.updated {voice}`, `voice.deleted`, `consent.check {ok, owner?, speakerName?, consentId?, at?, reason?}`, `script.get {lines: [{id, text, language}], recorded?: lineId[]}`, `clip.ack {lineId, take, ok, reason?, clips?}`, `train.progress {stage: queued|preparing|training|evaluating|done|failed|cancelled, progress 0..1, step?, totalSteps?, etaSec?, loss?, message?}`, `eval.report {metrics: {speakerSimilarity, utmos, cer, ttfaMs, rtf} or [{key, value, target?, better?, label?, unit?}], samples?: [{id, label, text?, audio}], summary?, at?}`, `ab.pair {pairId, text?, samples: [{id, system, audio}, {id, system, audio}]}`, `error {message, about?}`.
  - A voice: `{id, name, owner: self|other, speakerName?, language?, status: consent|recording|training|ready|failed, consentOk, clips, minClips (default 20), targetClips, minutes?, progress?}`.
- **Consent comes first, and only the core can grant it.** A state machine (`consent.ts`): own voice → owner → attestations; someone else's → owner → speaker (name, relationship) → a recorded consent statement read aloud by the speaker (at least 5 s, audible; the text names them and the date) → five attestations (present and agreeing, 18+ or guardian, no impersonation or deception, stays on this Mac, delete on withdrawal). Submitting sends `consent.record {owner, speakerName, relationship, attestations: [{key, text, agreed}], statement: {text, encoding: "wav", sampleRate, durationMs, audio}, agreedAt, version: 1}`. Record and Train unlock only when the core answers `consent.check {ok: true}`; reopening a voice asks `consent.check` again, and `ok: false` for a voice the UI thought granted resets the flow. Renaming the speaker discards their statement. **B: store the record and statement audio with the voice, refuse `clip.saved` and `train.start` without one, and delete everything on `voice.delete` (that's how consent is withdrawn).** Research 03 §4: "Get the speaker's consent and keep licence records for any voice."
- **Clips.** `clip.saved {lineId, text, language, take, encoding: "wav", sampleRate: 24000, channels: 1, bitsPerSample: 16, durationMs, peak, rms, audio}` (base64 WAV in the JSON frame, like `tts.chunk.pcm`). Recorded raw: Voice Lab opens its own mic with echo cancellation, noise suppression and auto gain **off** (they smear training data), separate from the stage's 16 kHz voice input. Leading/trailing silence is trimmed (250 ms kept). Takes the UI can tell are bad (under 0.8 s, quieter than −45 dBFS RMS, clipped, over 30 s) aren't sent. A 30 s take is ~1.9 MB of base64: **B: keep the WebSocket max message size at least 4 MB** (uvicorn's default 16 MiB is fine; `websockets`' own default of 1 MiB is not). Acks for an older take of a line are ignored.
- **Blind A/B.** The core sends two samples labelled by system (e.g. `base`, `adapter`); the UI decides which plays as A with a per-session secret seed mixed with the pair id (stable across re-renders, ~50/50 — unit-tested), requires both to be played to the end, reveals the systems only after the choice, and sends `ab.result {pairId, choice: A|B|same, preferred, other, shown: {A, B}, listened, decisionMs, tally}`. The tally includes an exact two-sided binomial p-value and the A-position share (position bias check). **B: don't pre-shuffle or hint the system in `id`.**
- **Verified in the browser preview** (stand-in cores, synthetic mic via `#/voicelab?fakemic`), light and dark: Memories search (one query for four keystrokes), inline edit (`memory.upsert` sent), simulated failure rolled back with a toast, two-item delete with the sheet (`memory.delete {ids}`), infinite load (offset 40), All characters + About Her filters, hand-injected results (bad items dropped, second timestamps), offline states for both windows. Voice Lab: someone-else consent end to end (short statement refused, 7 s accepted, all five boxes, granted on the core's reply), recording with Space (a 0.4 s take refused locally and not sent), six clips → training progress → ready → report, A/B with reveal and the `ab.result` payload. **Not verified:** a real microphone (mic permission prompt, levels, WebKit in the Tauri app), anything against B's core.
- **Found while testing:** React's dev double effects sent the first memory query twice, so a single reply was taken as the answer to the stale one. The window no longer re-asks the same filter.

## 2026-11-26 — M3 (A): four animation layers, realism pass, Hindi visemes, animation tuner

- **One layer model for every renderer** (`src/avatar/layers/`). `LayerAnimator` is pure (no DOM) and turns state, emotion cues, cursor look and "a gesture is playing" into one frame of abstract numbers each frame. Renderers map that frame onto their own parameters (`mapping.ts`: Cubism params for Live2D and Iki, joint channels for VRM). The layers, bottom to top:
  1. **Base life**: breath (each cycle a little longer or shorter), log-normal blink intervals with double blinks, micro-saccades, occasional look-away and glance-back, slow weight shift.
  2. **State posture**: idle / listening / thinking / speaking / working / sleeping / waking. Each state's offsets cross-fade on critically damped springs, so a state change never snaps. Waking turns into idle after 2.4 s. Thinking cues `think_chin` once, but only into a pause.
  3. **Gestures**: still each renderer's own. While one plays, the posture and the state gaze duck by 85 %, so a hand-to-jaw gesture still meets the face when the state changes mid-gesture. When a gesture ends, the body settles with a small damped sway and a weight shift.
  4. **Face**: emotion holds 5 s, then decays with a 3 s half-life unless the core re-sends it; a new emotion cross-fades with the old one. Lip sync and look-at.
- **Per renderer.**
  - **Iki** honours states now; before, `setState` only moved the thinking gaze. IkiMotion keeps its own blinks; the animator adds blinks on gaze shifts and on waking. The state gaze goes through `setGazeTarget`, so the head follows the eyes. A gesture's own expression wins while it plays, then the emotion's comes back (replaces the old `setTimeout` stops). Breath tempo comes from the posture only when it differs (asleep).
  - **Live2D**: the engine's auto-blink is switched off when the model has standard lids, and our blinks drive them. Emotion → `expressionMap` is chosen per frame with hysteresis, and the face extras (smile, brows, lids) show emotion even on packs without expressions (Hiyori).
  - **VRM**: its own blink and state code are replaced by the animator. Emotion levels blend several VRM expressions during a cross-fade.
  - **Arms and shoulders**: the posture never writes arm or elbow channels. A unit test holds this. VRM shoulders stay within ±8° (−3° asleep).
- **Her reply ending no longer resets the face.** The last emotion now decays on its own. A new turn, a barge-in or a character switch still fades it out at once.
- **Working state from tools**: the stage listens for `activity://working` from the Confirm window. Working puts her in the working posture (head down and aside, lids lowered, stiller, fewer blinks), unless she is speaking or listening. When the tool finishes she goes back to idle, if she is still in working. The stage also applies `hikari.micMode` / `hikari.micDevice` when Settings changes them (`storage` event).
- **Hindi visemes** (`lipsync/phonemeMap.ts`, `engine.ts`):
  - **Language per phoneme.** It is decided from the phones around it: retroflex, aspirated, dental, nasal-vowel and tap-r phones mean Hindi; ɹ æ θ ð ɜ w and English diphthongs mean English. The chunk's `language` is the fallback, and Hinglish defaults to Hindi. So Hindi ə (अ) is a full, open vowel and English ə a reduced one.
  - **Aspirated and breathy stops.** ʰ releases with a short puff; ʱ with a longer, wider murmur. Aspirated bilabials keep at least 60 % closure.
  - **Retroflex and other phones.** Retroflex stops are a little more open than dentals. The ɽ flap yields to its vowels. Added ɭ, ʐ and anusvara tokens (ⁿ/ṃ, which never close the lips).
  - **Cleanup.** Stress marks and tie bars are stripped.
  - **Closure on short bilabials.** The m/b/p closure ramp is now at most a third of the stop, so a 36 ms "m" in fast speech still seals.
  - 9 new tests use Hindi and Hinglish phoneme sequences.
- **Animation tuner** (dev only, `#/tuner?id=<character>`; `main.tsx` mounts it under `import.meta.env.DEV`). It loads any character. You can trigger states, gestures (protocol tags plus the pack's signatures and motionMap), emotions with intensity, Hindi/Hinglish/English test phrases (phoneme timings run through the real lip-sync engine, no audio needed) or held visemes. Every layer number has a live slider, and live bars show state weights, blink, gaze, emotion and weight shift. "Copy tuned numbers" copies only the changes as JSON, to paste into `layers/tuning.ts`. Overrides are stored per character in `localStorage` (`hikari.tuning.<id>`) and only dev builds read them back, so they can't ship.
- **Verified in the browser preview** (Vite dev, the tuner, magnifying the WebGL canvas):
  - **Lu Guang (Iki)**: idle, thinking (eyes up), working (lids lowered, looking down), sleeping (eyes shut, head bowed). `think_chin` kept his fingers on his jaw when switched to listening mid-gesture, then returned to rest with the listening tilt; shoulder and sleeve intact. Joy decayed from 0.79 to 0.23 in 10 s. The Hindi phrase opened and closed the mouth.
  - **Hiyori (Live2D)**: thinking (eyes up to the viewer's right), listening (tilt, eye contact), working (head down-aside), sleeping (eyes shut). Our blinks run with the engine's off, and the look-away and glance-back blinked on its return. A tap motion played through a state change. No console errors.
  - **Tuner**: slider edits save the diff to localStorage, and reset clears it.
  - **Not verified**: VRM visually (no sample model on this machine; covered by unit tests only), the Tauri app itself, `activity://working` end to end, and the CPU cost of the extra per-frame work (small: no allocations beyond a few objects per frame).

- **Settings window** (`apps/desktop/src/settings/`): General (launch at login, talk mode, input device, default language) · Providers (provider + model per capability `llm`/`stt`/`tts`/`embed`, live `provider.status` badges with latency and the stand-in provider during failover, API keys) · Performance (hardware profile, memory meters) · About. Local providers offer an **"Automatic" model** = the core picks the size for the hardware profile.
- **API keys live only in the macOS Keychain** (`src-tauri/src/secrets.rs`, `keyring` =4.2.0, default `v1` feature → apple-native-keyring-store 1.0.3 / keyring-core 1.1.0). One generic-password item per provider: service `com.hikari.companion`, account = provider id (`groq`, `gemini`, `openai`, `sarvam`, `elevenlabs`, …; `[a-z0-9_-]{1,32}`). Commands `secret_set` / `secret_status` / `secret_delete` return `{provider, saved, last4}` only: the webview never gets a key back. Keys are trimmed; empty, whitespace-containing or > 1024-char keys are refused (the UI also refuses < 12 chars and warns, without blocking, on an unexpected prefix). `last4` is withheld for keys under 12 chars. Keychain calls run on a blocking thread. The lockfile gains the Linux/Windows keyring stores too (only the Apple store is compiled on macOS).
- **How the core gets keys (B, decide in M4):** proposed: the sidecar supervisor reads the Keychain in Rust and passes keys to the core in its environment at spawn (`HIKARI_KEY_<PROVIDER>`), and respawns it when a key changes. Not over the WebSocket, and not by the Python process reading the Keychain itself (a different binary gets a Keychain access prompt per item). Until the supervisor exists, a dev core can read them with `security find-generic-password -s com.hikari.companion -a groq -w`.
- **Settings the core needs** (provider/model per capability, `profile`, `language`) are saved by Rust as `settings.json` in the app config dir (`settings_store.rs`: JSON object ≤ 64 KB, atomic write) and broadcast to every window as the Tauri event `settings://changed`. **The protocol has no message for them, so nothing is sent to the core yet.** Proposed addition for B (protocol PR, both sides):
  - `settings.update` (ui → core), sent on connect and on every change: `{ profile: "lite"|"standard"|"max", profileSetting: "auto"|…, language: "auto"|"en"|"hi"|"hinglish", providers: { llm|stt|tts|embed: { provider: string, model: string /* "auto" = core picks for profile */ } } }`. The core treats `providers.*` as the head of its router chain (failover continues past it) and answers with fresh `provider.status` for each capability.
  - Optional `provider.status` request (ui → core, empty payload) so a panel opened later gets the current table; today Settings only sees statuses sent while it's open.
  - Optional `secrets.changed` (ui → core) `{ provider }` if B prefers hot-reloading keys to a respawn.
- **Hardware profiles**: Light (8 GB) / Balanced (16 GB) / Max (32 GB+), plus Auto = the largest profile whose minimum this Mac meets (−5 % tolerance). Picking a profile above the Mac's memory shows a warning, not a block. Budgets shown (≈5 / 8 / 13 GB of models) are the research estimates.

## 2026-11-26 — M7 (A): confirm dialog, audit log, Activity window, "working" signal

- **Who asks.** The UI asks whenever `needsConfirmation` is true *or* the tier is `act`/`sensitive`, even if the core sent `needsConfirmation: false` (defence in depth). `read` calls without the flag run unasked but are still logged. **B:** set `needsConfirmation: true` for every act/sensitive call and actually wait for `tool.confirm`; otherwise the dialog can't stop anything.
- **Confirm window** (`src/activity/Confirm.tsx`, 440×260, always on top, all Spaces): exact `summary`, tool name, tier badge (sensitive = orange with a warning triangle and an orange top rule; pink stays "Hikari", not "careful"), up to 4 key args (secret-looking keys masked). **Deny is the default** (focused, Return and Escape both deny); the red close button denies everything waiting. **Allow** is disabled for the first 1 s after a request appears (a keystroke or click meant for another app can't land on it); for `sensitive` it is **press-and-hold 1.5 s** (pointer or Space; a click or Return never approves). **60 s auto-deny** with a ring + "Denies in N s"; requests queue one at a time and each one's clock starts when it reaches the front. The window shows/focuses itself via the window API (`core:window:allow-show` added to the panels capability) and hides when the queue empties.
- **One writer.** Every window gets the same `core://event`s, so to avoid duplicate lines the **Confirm window is the audit log's only writer** (`guard.ts` `ActionGuard`): it is created hidden at startup and never closed (close = hide), so it always runs, and it is the window that knows the decisions. Activity only reads (and follows `audit://appended`). The stage was the other candidate but belongs to M3 and doesn't know the decisions.
- **Audit log** (`src-tauri/src/audit.rs`): JSONL in `<app data>/audit/audit.jsonl`, records `request` / `decision` (approved, denied, auto_denied, panic, cancelled + via click/voice/timeout/panic/window_closed/disconnected and time waited) / `result` / `panic`. Append-only from the UI: no edit/delete command; Rust stamps `ts` (the UI's is ignored), accepts only those four kinds, caps a line at 64 KB, rotates at 2 MB keeping 3 old files (~8 MB). Args and results are redacted (password/token/api key/cookie/… keys) and truncated in the UI before writing. **Clear** asks in a native dialog from Rust (the webview can't skip it) and leaves a `cleared` line; **Export** uses a native save dialog in Rust (no write-anywhere path from the UI); **Show in Finder** = `open -R`. 5 Rust tests (temp dirs).
- **Activity window**: timeline per call (newest first, day headings), status (waiting / running with live elapsed / done / failed / denied / timed out / stopped), tier, time, duration (approval → result), result or error, expandable args/decision/result; panic and clear shown as divider marks; filters (status group, tier), search (tool, summary, args, error, callId; ⌘F), Export…, Show in Finder, Clear….
- **Panic**: the stage already barges in and sends `tool.confirm {callId:"*", approved:false}` on `hotkey://panic` (⌘⇧Esc, tray). The Confirm window listens to the same event: drops its queue, hides, writes a `decision: panic` per waiting call plus one `panic` record (waiting + running callIds), and turns "working" off. It does not send extra per-call denials (the `*` covers them).
- **"Working"**: the guard tracks calls that are approved (or unconfirmed read calls) without a result and emits **`activity://working {working: boolean, tool?: string}` to the stage window** on every change (off after a result, panic, core disconnect, or 3 min without a result). The stage doesn't listen yet: **hook for the stage/avatar owner (M3)** — in `StageRuntime.wireTauri()` add `listen("activity://working", e => …)` that sets `avatar.setState("working")` + `useStage.setState("working")` when `working` is true and nothing higher-priority (speaking/listening) is active, and back to `idle` when false (only if the state is still `working`); `isBusy()` already treats any non-idle state as active. A core `state: "working"` keeps working as before.

## 2026-11-25 — VRM renderer (A, M3)

- **`VrmAvatar`** (`apps/desktop/src/avatar/vrm/`) renders `.vrm` packs (`renderer: "vrm"`) with **three 0.187.0 + @pixiv/three-vrm 3.5.5** (exact pins; 3.6.0 was one day old, 3.5.5 is the version `docs/RESEARCH.md` picked). `loader.ts` imports it lazily: three and three-vrm are a separate ~770 kB chunk (192 kB gzip) that loads only when a VRM pack is shown; the main bundle has no three.
- **VRM 0.x and 1.0**: one code path. `VRMUtils.rotateVRM0` turns 0.x models to face +Z, and three-vrm maps 0.x expression presets (a/i/u/e/o, joy, sorrow, fun, blink) to the 1.0 names. One catch found in testing: 0.x normalized bones keep the model's own −Z-facing frame, so arm rotations went *up* instead of down. Every bone rotation is conjugated by the half turn for 0.x (`toVrm0Frame`: x and z flip sign).
- **Same contract as Live2D/Iki**: transparent WebGL canvas, no rAF of its own (the stage's frame scheduler calls `update(dt)`: 60/30/0 fps). `isBusy()` is true while a gesture plays, the pose spring is still settling or the eyes are catching up, and false at rest, so idle drops to 30 fps. Hit test reads back one pixel after the render, as Iki does, and anything above the projected neck counts as `head`. `destroy()` disposes geometries, materials and textures (`VRMUtils.deepDispose`) and the renderer, and forces context loss.
- **Framing**: waist up, facing the camera, head near the top edge. The framing is measured once, at rest, so a gesture never shifts it. It fits height or width, whichever is tighter, and `pack.scale` < 1 zooms out.
- **Motion** lives in pure modules (`pose.ts`, `gestures.ts`). A pose is a small set of joint angles in degrees: torso/neck/head Euler; per arm `armDown`/`armFwd`/`armTwist`/`elbow`/`hand`/`curl`/`index`. These map to normalized humanoid bones, with the elbow as a forward-only hinge and hard joint limits. Gestures are eased offsets from a natural rest pose (arms down, elbows soft, fingers relaxed) and run through a critically damped spring, so an interrupted gesture blends instead of snapping. Arm targets were tuned with forward kinematics on a VRoid-proportioned skeleton: hand at the chin, palm to the brow, palms meeting for a clap, forearms folded. Unit tests hold those reaches.
- **Gestures**: all 14 protocol tags (wave, point, shrug, clap, cross_arms, think_chin, facepalm, bow, nod, head_tilt, shy_look_away, laugh, pout, head_pat_react). A pack's `motionMap` can alias names onto them. Stage taps play `head_pat_react` (head) or `wave` (body). **Idle**: breathing in chest and shoulders, slow weight sway, head drift, slight arm and finger life, blinks every 2–6 s (sometimes double), and small head beats while speaking. **States**: listening leans in, thinking looks up and aside, sleeping lowers the head with eyes closed.
- **Lip sync**: visemes go to the VRM `aa/ih/ou/ee/oh` expressions (`visemeWeights`). The total is normalised to ≤ 1, because mouth morphs stack, and scaled down under a smile. **Emotions** map to `happy/angry/sad/relaxed/surprised`; 0.x has no `surprised`, so it falls back to a round mouth. A pack's `expressionMap` can name a custom expression. **Gaze**: the eyes use three-vrm's lookAt toward a target at the camera's distance, so (0, 0) means eye contact. The head takes 38 % of the turn.
- **Verified** in the browser preview with two pixiv sample models: VRM1_Constraint_Twist_Sample (1.0) and three-vrm-girl (0.0). Both were downloaded only to a gitignored folder and deleted afterwards. Checked: rest pose, every gesture at its peak, aa/oh lip shapes, joy/angry/sorrow/surprised, look-at in both directions, the three states, the hit test (head, body and empty space) and dispose (context lost, canvas removed). **Not verified**: inside the Tauri app (CSP already allows `blob:` for embedded textures and `hikari-pack:` for imports), Studio preview of a real imported pack, CPU cost at the idle tier, and models with unusual proportions (very long arms or chibi). It echoes your voice back (PTT release, or end of speech when always-listening) with loudness-based phonemes, and speaks `text.in` with macOS `say` (Lekha for Devanagari, Tara otherwise). Replies go to all UIs, so the console can make the app speak.
- **Verified:** dev and release builds deliver 50 frames/s (20 ms) to the core. A console-driven reply played in the app with lip sync, caption and the speaking state, with no false barge-in during a 4.8 s reply. **Not verified:** echo cancellation with speakers (output was AirPods), the ⌥Space press path with a real key (synthetic keys need Accessibility), and an always-listening barge-in by a real voice.

## 2026-11-20 — Phase 0 / M0 (A)

- **Hands-on cursor test** (`apps/desktop/dev/cursor.swift` moves the real cursor; click-through toggles are logged at debug level). It found a bug: the hit test answered from the *previous* pixel readback, so with the cursor resting on her she stayed click-through until the mouse moved again. Fresh readbacks now apply immediately (`onHitChange`). After the fix, 6/7 points were correct within 0.5 s: face and cardigan clickable; leg gap, empty window area and far away pass clicks through. The 7th point was on her hair's outer edge, so inconclusive. **Not tested by me:** clicking and dragging (synthetic clicks need Accessibility permission for the terminal, which isn't granted, and I won't change security settings) and eye-follow (screenshot caught a blink).
- **A/V sync measured: pass.** `pnpm -F desktop avsync` (dev/avsync.sh → `src/dev/avSyncProbe.ts`) plays 10 sharp /a/ bursts through the real chain and compares each burst's *heard* onset (AudioContext output timestamp, device latency included) with the first *displayed* frame where the mouth is half open. Result on an M2 with a Bluetooth headset (output latency 111.6 ms) at 30 fps (Low Power Mode): **mean −1.4 ms / +6.9 ms in two runs, spread under 2 ms, jitter 0.5 ms** (target ±40 ms). 60/120 Hz not yet measured. Ground truth is WebAudio's reported output latency, not a microphone; real Bluetooth latency can differ from what macOS reports.
- Three sync bugs the probe found, all fixed:
  1. **Silence blended too strongly** (`sil` dominance 1.5, 80 ms spread, plus the m/b/p closure gate): isolated vowels after a pause opened to only 0.40, and late. Silence is now a weak resting posture (0.4, 30 ms, no closure gate), and vowels open to ~0.8.
  2. **Jaw loudness read from an AnalyserNode**, which sees audio when it's *processed*, 100+ ms before it's *heard* on Bluetooth. Loudness now comes from the decoded samples at the audible time (`PlaybackQueue.energyAt`). The spectral fallback (used only with no phonemes) still reads the analyser.
  3. **Lips sampled for render time, not display time**: one frame late (+33 ms at 30 Hz). Lip sync now samples at audible time + the smoothed frame interval.
- **Deep idle tried and rejected (user call: "30 fps at idle was better, this looks lagging").** A 15 fps tier after 15 s of inactivity measured 19.4–21.5 % vs 24.7 % at 30 fps: too little saving for visibly choppier motion. Idle stays at 30 fps and ~25 % of a core is accepted for now. Two findings from the experiment:
  - A release build that renders **zero frames** still costs ~9 % (Hikari's process ~5 %, the rest WebKit). Disabling the cursor poll didn't change it, and driving the calm tiers with timers instead of rAF saved only ~2 points. So the fixed cost is WebKit/WKWebView overhead, not our render loop. Revisit with Instruments if the budget matters later.
  - Kept: a cursor moving **far** from her no longer forces 60 fps (only within 160 pt of the window does). Eyes still follow at the 30 fps idle rate, so using the mouse elsewhere doesn't double her cost.
- **Render tiers** (`src/stage/frameScheduler.ts`): 60 fps active (speaking, gestures, hover, listening/thinking, eyes catching up, 800 ms tail), 30 fps idle, 0 when hidden via the tray. Skips rAF ticks, so it's vsync-aligned on 60/120 Hz; under macOS Low Power Mode WebKit caps rAF at 30 fps and both tiers get every tick.
- **No pause on `document.visibilitychange`**: WebKit reported this floating panel as `hidden` at boot while it was on screen (release build, Chrome frontmost). Only the tray's explicit hide pauses rendering.
- **Cursor poll** reads CoreGraphics (`CGEventGetLocation`, thread-safe, no TCC) and caches window geometry from window events. Four Tauri getters at 30 Hz were each a synchronous main-thread round trip. Polls at 30 Hz near her or while the cursor moves, 8 Hz otherwise, and not at all while hidden.
- **Production-only bugs found by testing the release build** (dev serves without Tauri's CSP or the custom protocol, so none showed in dev):
  1. Pixi v8 needs `import "pixi.js/unsafe-eval"` under a CSP without `unsafe-eval`; otherwise it fails at init.
  2. Pixi decodes textures in a `blob:` Worker, which the CSP blocks, so loading hung forever with no error. Fix: `loadTextures.config.preferWorkers = false`. The CSP stays strict.
  3. Pixi resolves root-relative URLs under `tauri://` to `tauri://characters/…` (host dropped). Model URLs are now absolute.

In both, about 20 points are WebKit rendering and compositing Live2D; the app process (~4 %) is mostly UI-side compositing. The spec's "idle CPU < 3 %" can't be met while idle stays at 30 fps (§9.5): cost scales roughly with frame rate. This needs a product decision (see PLAN open questions).
